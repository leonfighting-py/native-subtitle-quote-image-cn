# 竖屏与方形素材

读取时机：源视频是竖屏（9:16 等）或方形，而不是 16:9 横屏时。抖音、快手、小红书、视频号、B站竖屏切片都属于这一类。

横屏的默认参数在竖屏上会直接失效，而且失效方式是“看起来跑通了、其实一个字都没圈到”，所以必须先读本文再动手。

## 默认参数为什么不能用

默认字幕带 `--band-top 0.78 --band-bottom 0.96` 和服务端 `--band-center 0.88`，都是按**横屏烧录字幕压在画面最下方**这一经验设计的。

实测：1080×1920 竖屏素材，字幕位于画面高度 0.58–0.70：

| 参数 | 实际圈到的区域 | 结果 |
|---|---|---|
| 默认 `0.78–0.96` | y=1497–1843 | **完全错过字幕**，圈到的是纯背景 |
| `0.55–0.75` | y=1056–1440 | 完整包住字幕 |

`--band-center` 同理：默认 `0.88` 在竖屏上采样的是 y≈1690 的区域，也在字幕下方。

**竖屏字幕没有固定位置。** 短视频 App 里字幕常压在中下部，访谈类竖屏可能压得更低，去掉 UI 后的二次剪辑又会变。所以必须实测，不要照抄本文的区间。

## 第一步：先测字幕带

```bash
python3 "<SKILL_DIR>/scripts/native_subtitle_stitch.py" band VIDEO \
  -t 5 --band-top 0.55 --band-bottom 0.75 --out band-portrait.jpg
```

从 `0.55–0.75` 起步，看两条红线是否完整包住字幕：

- 字幕在红线**上方** → 整体上移，例如 `0.45–0.65`；
- 字幕只有一半在红线内 → 扩大区间，例如 `0.50–0.80`；
- 红线范围内是大片空白 → 区间收窄或平移。

竖屏画面高、字幕行数少，区间扩大时很容易把大量无文字背景带进字幕条。宁可多测两次，也不要一次开到 `0.30–0.95`。

同一支视频至少抽查开头、中段、结尾三个时间点——短视频的转场和贴纸位置经常变化。

## 第二步：选布局

### 竖屏源做 3:4 的代价

实测：1080×1920 源用 `--aspect 3:4 --width 1440`，输出 1440×1920，但主画面只取到源画面纵向中段的 1180px，**裁掉 740px，占画面高度的 38.5%**。

更糟的是裁切窗口默认居中：如果源画面自带字幕恰好落在中段，它会被裁进主图，与脚本模式绘制的第一句形成**重字**。

所以竖屏源不要默认套 3:4。

### 实测可用的四种写法

| 目标 | 命令要点 | 实测输出 |
|---|---|---|
| 保留竖屏原始比例 | `--layout natural` | 1080×1178（`--frame-bottom 0.55` 时） |
| 固定 9:16 | `--aspect 9:16 --width 1080` | 1080×1920 |
| 方形 1:1 | `--aspect 1:1 --width 1440` | 未实测，按同一套逻辑验证 |
| 竖屏源做 3:4 | 不推荐 | 裁掉 38.5% 纵向画面 |

`--aspect` 接受任意 `宽:高`，不只是 `3:4`。竖屏内容的自然画幅就是 9:16，硬转 3:4 会损失画面，也会让主画面里的人物被切头切脚。

```bash
python3 "<SKILL_DIR>/scripts/native_subtitle_stitch.py" render-script VIDEO \
  --script script.json --out out-916.jpg \
  --aspect 9:16 --width 1080
```

## 第三步：源画面已有字幕时避开重字

脚本模式会把已审核台词画到真实画面上。如果**源画面本身也有烧录字幕**，两者会叠在一起。

用 `--frame-bottom` 先把源字幕区裁掉，再让字幕条从裁切后的画面里采样：

```bash
python3 "<SKILL_DIR>/scripts/native_subtitle_stitch.py" render-script VIDEO \
  --script script.json --out out.jpg \
  --aspect 9:16 --width 1080 \
  --frame-bottom 0.55 --band-center 0.5
```

- `--frame-bottom` 是**源画面**的下裁切边界，`0.55` 表示只保留上部 55%，源字幕（0.58–0.70）正好被裁掉；
- `--band-center` 相对**裁切之后**的画面，所以裁掉字幕区之后才能用回接近 0.5 的值；
- 裁切窗口不能再拉回原高度——`--frame-bottom` 之后高度变小是正常的，不要用 `--width` 去“补齐”。

如果源画面的字幕**就是要保留的内容**，那属于原生字幕模式，本来就该用 `render` 而不是 `render-script`。两种模式的边界见 [SKILL.md](../SKILL.md)。

## 竖屏原生字幕模式

原生模式在竖屏下照常工作，注意这两点：

- 主画面从画面顶部一直到 `--band-bottom`。竖屏字幕位置偏高时，主画面实测会显著变矮，这是正确行为，不要为了“主图够大”把 `--band-bottom` 往下压；
- 竖屏源做固定画布时经常需要留边。实测 1080×2208 的竖屏拼图套 9:16 固定画布，输出 1080×1920 且**左右留黑边**，因为竖屏拼图比 9:16 更扁。这是 `--fit crop` 的预期取舍，不是条间距。

| 布局 | 命令 | 实测输出 |
|---|---|---|
| natural（默认） | `render --band-top 0.55 --band-bottom 0.75` | 1080×2208 |
| 固定 9:16 | 同上加 `--aspect 9:16 --width 1080` | 1080×1920，左右留边 |

## 字幕条密度

字幕条密度公式不变（`clamp(1 - 字幕条数 × 0.075, 0.48, 0.82)`），但竖屏的观感不同：

- 竖屏画面本身信息密度高，主画面占比低于 0.70 时会明显“压扁”；
- 优先用 4–5 个时间点（主画面 + 2–3 条字幕）。竖屏长图在手机上很高，条数过多会让整张图失去可读性；
- 字幕条被撑高、主图变小的情况，先检查是不是只有 2–3 个时间点导致自动比例算高了，而不是去手动传 `--hero-fraction`。

## 竖屏源的常见干扰

- 底部常有 App 的水印、账号 ID、音乐条或评论气泡，取帧时避开；
- 上下黑边（letterbox）很常见。若黑边进入主画面，用 `--frame-top` / `--frame-bottom` 裁掉；
- 竖屏素材经常是二次剪辑，同一支视频里画幅可能变化（例如中段插入了横屏素材），渲染前先看候选帧总览确认；
- 旋转元数据：部分手机导出视频带 rotation，FFmpeg 读出的宽高可能和播放器不一致。`band` 预览发现画面方向不对时，先确认源文件本身，不要靠反复调 `--band-top` 补救。
